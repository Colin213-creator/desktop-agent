## 1. 背景

课题大作业，同时要能作为求职作品展示。

起点是工作目录里已有的 `agent.py`：它已经跑通工具调用闭环（工具注册表、JSON Schema 说明书、
多轮记忆、工具失败回灌），有 7 个工具，但能力停在"查信息"——查天气、查磁盘、查端口。
它不会动手，也不算真正的智能体。

另外两个既有事实决定了这次要动的改造：

- 脚本里写死的 `qwen2.5:3b` 已从本机删除，现在执行必报 404。
- 原先配置的 `deepseek-v4-flash:cloud` 已于 2026-09-25 退役。
- 实测可用的 `gemma4:31b-cloud` 具备 `completion / thinking / tools / vision`，
  上下文 262144，工具调用往返约 0.3 秒，是本次视觉路线的技术前提。

## 2. 项目定位

一句话：**一个会学习、可远程代操作的 Windows 桌面智能体。**

和相近概念的区别：

| 对象 | 差别 |
| --- | --- |
| 聊天机器人 | 它只回答，本项目的智能体会实际操作系统 |
| RPA | RPA 走固定流程，本项目每步看结果再决定下一步 |
| 普通 GUI 自动化脚本 | 本项目用自然语言入口，能拆任务、能重试、能沉淀经验 |
| 通用 RAG 问答 | 本项目在检索到流程后真的把流程执行出来 |

## 3. 用户与场景

主用户是开发者本人，运行环境是自己这台 Windows 笔记本（Windows 10 Pro 24H2，
支持交互式桌面，可模拟键鼠）。

典型使用：用一句自然语言描述一个需要跨应用完成的任务，智能体自行拆解、执行、核对、
在失败时调整策略，最后给出结果与运行记录。

预置六个演示场景，从"能动手"一路递进到"能证明自己没做完"。每个场景对应一项可测量的
能力，不靠功能数量堆场面：

| # | 场景 | 难度 | 证明什么 |
| --- | --- | --- | --- |
| 1 | 打开计算器算 1234 × 5678 | 入门 | 能真实操作界面 |
| 2 | 找出 D 盘最大的 5 个文件，生成表格并用 Excel 打开保存 | 中 | 跨工具、跨应用、能处理保存对话框 |
| 3 | 按《报销操作规范》生成一份报销单 | 中高 | SOP 检索真的影响执行，不止于回答 |
| 4 | 制造"看着完成、实际没完成"的陷阱，看它能否自证失败 | 高 | 独立验证者的价值，单体自评容易误判 |
| 5 | 人手演示一遍操作，智能体学会后独立复现 | 高 | 从示范中学习，而不是写死流程 |
| 6 | 从另一台设备发任务，被控端执行并回传画面 | 高 | 架构可远程扩展 |

## 5. 总体架构

分五层，核心是一个循环。

```
感知  ── 截图 / 活动窗口 / 光标 / 控件树
  ↓
决策  ── 规划器 + 执行器 + 验证器（gemma4:31b-cloud）
  ↑↓
记忆  ── 会话历史 / 本次轨迹 / 技能库 RAG / SOP 知识库 RAG
  ↓
执行  ── 鼠标键盘 / 启动程序 / 文件读写
  ↓
安全  ── 风险分级 / 人工确认 / 急停 / 预算
```

主循环：

```
任务
  → 检索技能库与 SOP（RAG）
  → Planner 规划（产出带预期结果的步骤）
  → Operator 执行一步
  → 截图观察
  → Verifier 独立验证（达成 / 重试 / 重规划）
  → 失败累计时由 Recoverer 介入重定策略
  → 下一步，或收敛（成功 / 求助 / 中止）
```

设计约束：**核心循环不得依赖远程层与网页界面**。这两者是旁路，任一失效都不影响
在终端里完成一次完整任务。

## 7. 核心机制

### 7.1 三档定位

定位一个操作目标时按顺序降级：

1. **语义工具直做**：打开程序、输入文字、按快捷键，不需要定位。
2. **控件树精确点击**：从 UIAutomation 读出按钮、输入框、菜单项，按控件定位。
3. **视觉兜底**：截图交给视觉模型，让其给出归一化坐标，再换算成屏幕坐标点击。

降级的动因是准确率：控件树命中时几乎是确定性的，视觉兜底覆盖自绘界面。
每次动作后都要重新观察，不能连点一串再统一验证。

### 7.2 自验证

每一步执行后重新截图，向模型提问三件事：

- 当前步骤的目标达成了吗？
- 依据是截图中的什么？
- 如果没达成，原因是点偏、界面未刷新，还是前置条件不成立？

结论只有三种：`continue`、`retry`、`replan`。连续三次失败停止并求助用户，
不允许继续盲目尝试。

### 7.3 技能库 RAG

任务成功后把轨迹抽象成一条技能记录，包含任务描述、前置条件、抽象后的工具序列、
成功次数与平均步数。

检索管线：文档切分 → embedding → 向量召回 top-k → 重排 → 交给规划器判断是否可复用。
复用后仍需逐步验证；任何一步不成立立即退回现场规划。

度量：技能命中率、复用后步数下降比例、复用失败率。

### 7.4 SOP 知识库 RAG

导入操作规范类文档（Markdown / 文本 / 可解析的 docx），按标题与段落切分，
建立关键词与向量混合索引。规划前按任务描述检索相关段落，作为"操作依据"注入上下文。

与技能库的区别：技能库记录"以前怎么做的"，SOP 记录"规定应该怎么做"。前者来自经验，
后者来自制度，两者一起进规划上下文。

度量：检索命中率、注入后任务成功率变化。

### 7.5 多智能体编排

四个角色，职责单一，通过结构化 JSON 通信，不做自由聊天：

| 角色 | 输入 | 输出 | 调用时机 |
| --- | --- | --- | --- |
| Planner | 任务、技能与 SOP 检索结果、历史失败 | 步骤计划，每步带预期结果 | 任务开始与重规划 |
| Operator | 当前步骤、当前截图 | 一个工具调用 | 每一步 |
| Verifier | 步骤预期结果、执行前后截图 | `continue` / `retry` / `replan` 及依据 | 每一次动作之后 |
| Recoverer | 最近若干步与失败记录 | 新策略建议 | 连续失败三次 |

编排是确定性状态机：

```
Planner
  └→ Operator → Verifier ─continue→ 下一步
                     ├retry→ Operator（同一步换参数）
                     └replan→ Recoverer → Planner
```

**Verifier 使用独立上下文，看不到 Operator 的自我解释。** 这是这套编排的核心价值：
让打分的人和干活的人分开，避免执行者给自己的操作找理由。这一点会做对照实验验证，
不是写在文档里好看。

代价是每一步多一次模型调用；Verifier 固定使用本地小模型，抵消大部分成本。

## 8. 安全设计

动作分三级：

| 级别 | 例子 | 处理 |
| --- | --- | --- |
| 只读 | 截图、读文件、查磁盘 | 直接执行 |
| 界面操作 | 点击、输入、开关普通窗口 | 执行并记录 |
| 破坏性 | 删除、关机、覆盖文件、关闭有未保存内容的窗口 | 暂停，等待人工确认 |

另外三条硬约束：

- 全局急停热键，任意时刻可中断。
- 步数、时长、模型调用次数三个预算上限，触顶即停。
- 首次运行与调试默认在 `runs/_sandbox/` 内操作，不碰系统目录与用户文档目录。

## 9. 远程层

可插拔，独立于核心循环。

被控端在目标机运行 WebSocket 服务，接收任务、推送截图帧、回传执行状态；
控制端为浏览器页面，可提交任务、查看画面与日志、触发急停。连接使用一次性令牌。

实现目标是"能远程下任务并看到过程"，不是低延迟远程桌面。

## 10. 界面

本地网页单页：左侧实时画面，右侧滚动动作日志，当前步骤高亮，底部任务输入框，
顶部急停按钮。

任务结束后生成可回放报告页：任务描述、总耗时、步数、模型调用次数、
关键截图时间线、最终结果。

终端模式下保留纯文本输出，保证没有浏览器时也能完整演示。

## 11. 数据模型

轨迹 `runs/<timestamp>/`：

| 文件 | 内容 |
| --- | --- |
| `task.json` | 任务描述、开始与结束时间、最终状态、模型与版本 |
| `trace.json` | 每一步的工具名、参数、风险级别、截图前后文件、验证结论、耗时 |
| `step_XXX_before.png` / `step_XXX_after.png` | 该步执行前后的画面 |
| `report.md` | 自动生成的完成报告 |

技能记录 `skills/<id>.json`：技能名、触发描述、前置条件、工具序列模板、来源轨迹、
成功次数、平均步数、最近使用时间。

SOP 索引 `knowledge/index/`：切分后的段落、来源文件与位置、关键词与向量。

## 12. 错误处理

| 故障 | 处理 |
| --- | --- |
| 截图失败 | 重试一次，仍失败则降级为仅控件树模式并提示 |
| 模型超时 | 重试两次，仍失败则中止当前任务并保留轨迹 |
| 元素找不到 | 重新感知，最多一次重规划后求助 |
| 断网 | 提示并切换到本地模型，能力降级但流程可跑 |
| 用户中断 | 立即停止动作，已产生的轨迹完整落盘可回放 |
| 工具抛异常 | 异常信息作为工具结果回灌模型，由模型决定下一步 |

## 13. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 模型 | `gemma4:31b-cloud`（主）、`deepseek-r1:1.5b`（本地兜底） | 前者具备视觉与工具调用，后者保证断网可用 |
| 模型接入 | Ollama HTTP API | 已有部署，接口简单，可换成任意 OpenAI 兼容端点 |
| 截图 | `mss` | 比整屏 PIL 抓取快，多显示器支持好 |
| 输入模拟 | `pyautogui` + `pynput` | 前者动作完整，后者监听急停热键 |
| 控件树 | `uiautomation` | Windows 原生 UIA 封装，按控件名定位比坐标稳 |
| 向量检索 | 本地 SQLite 存向量 + numpy 余弦相似度 | 数据量小，避免引入重型向量库，检索逻辑可完整讲清 |
| Embedding | 本地 `bge-m3`（Ollama 拉取；不可用时退回 `nomic-embed-text`） | 中文任务描述与 SOP 需要中文语义质量 |
| 服务 | FastAPI + WebSocket | 同时承载本地界面与远程控制端 |
| 前端 | 单页 HTML + 原生 JS | 界面不是重点，减少构建链 |

## 14. 评估方案

固定 10 个任务，覆盖三类：单应用短任务、跨应用多步任务、需要查 SOP 的任务。

每次批量执行记录：成功与否、步数、耗时、模型调用次数、是否触发人工确认、失败原因分类。

对比四组配置，用来证明各模块确实有效：

1. 纯视觉（无控件树、无技能复用、无 SOP）
2. 混合定位（三档降级）
3. 混合定位 + 技能库 + SOP
4. 在 3 的基础上，把"执行者自评"换成独立 Verifier

第 3 组与第 4 组的差值，就是多智能体编排的净收益。另外单独统计高难演示场景的成功率，
其中"验证陷阱"场景单独统计误判率。

## 15. 验收标准

1. 一句自然语言触发，自动完成不少于 3 步界面操作。
2. 某步失败时能自动重试或停止并说明原因，不出现卡死。
3. 破坏性动作必须经人工确认才执行。
4. 每次运行都能回放：目录内具备轨迹与逐步截图。
5. 断网时给出明确提示并降级，不崩溃。
6. 六个预置演示场景现场跑通，其中至少三个属于"高难度"档。
7. 同一类型任务第二次执行时，步数有可测量的下降。
8. SOP 检索命中率可量化，并给出注入前后的任务成功率对比。
9. 独立 Verifier 相对执行者自评，在"验证陷阱"场景上的误判率显著更低。

## 17. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 视觉定位不稳 | 控件树优先，视觉只做兜底；每步后验证 |
| 云端模型断网或限流 | 本地模型降级；关键演示前置健康检查 |
| 自动操作误伤文件 | 风险分级 + 二次确认 + 初始只在临时目录操作 |
| 长任务超时 | 步数与时长预算；任务拆小 |
| 技能复用过拟合 | 复用必验证，失败立即回退现场规划 |
| 评估数据太少没有说服力 | 任务集固定且分类覆盖，报告只陈述可测指标 |
